# 可行、合理、正确是三件事：解码器状态的交叉表（028）

## 问题

SUMMON 那张消融表给过一个警告：去掉接触损失后，非碰撞分数升到 0.995，接触分数只剩 0.194——物体离人远一点当然不容易碰撞，但这不等于恢复对了。同一类混淆在我们的解码头里也存在：`status` 为 `ok` 只说明候选域里存在一组自洽解，不说明它是对的。本模块把状态与结果交叉列表，回答“剩余损耗里有多少是没给答案，有多少是给错答案”。

## 方法

只读 `output/layout-recon/matrix023/off{0,1000,2000}/*/multi-*/result.json` 里已有的 324 行（12 间 × 3 访次 × 3 严重度 × 3 次手机噪声实现），取 `status`、`all_instances_hit`、`f1`，不重跑任何推断。

复现：`python -m analysis.layout.status028`，输出 `output/layout-recon/status028/status028.json`。

## 结果

324 行：状态 `ok` 266 行（82.1%），整屋全中 156 行（48.1%）。

| 状态 | 全中 | 未中 |
|---|---|---|
| ok | 156 | 110 |
| proposal_conflict | 0 | 45 |
| search_budget_exhausted | 0 | 11 |
| no_proposals | 0 | 2 |

按严重度拆：

| 严重度 | n | 状态 ok | 全中 | ok 但错 |
|---|---|---|---|---|
| 0 | 108 | 105（97.2%） | 62（57.4%） | 43 |
| 0.5 | 108 | 92（85.2%） | 57（52.8%） | 35 |
| 1 | 108 | 69（63.9%） | 37（34.3%） | 32 |

## 怎么读

无扰动档里解码器几乎总有答案（105/108），但只有 62 次是对的。也就是说，这一档的剩余损耗基本不是“求解器放弃”，而是“求解器给出了一组自洽但错位的摆法”。反过来，非 ok 的 58 行一次都没中——状态确实拦住了无法求解的记录，它只是没有能力区分“自洽但错”的那 110 行。

对论文的直接后果：三层都要分开报三个数——可行率（status ok）、整屋中心全中、以及占地 IoU≥0.5。把 `ok` 当成功率会被审稿人一眼看穿；把“可行但错”藏起来，正是 SUMMON 那张表在提醒的事。

## 边界

只统计已存结果的计数与状态，不涉及新推断、不改任何阈值；`ok` 的定义来自现有解码头，本模块不重新定义它。324 行共享同一批 12 间房与同一生成族，外推范围与 024 文档相同。
