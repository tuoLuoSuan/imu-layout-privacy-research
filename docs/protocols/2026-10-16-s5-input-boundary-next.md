# S5输入边界：离线结论与下一轮最小协议

2026-10-16。当前手机接收0.2.3与手表0.3.4保持。三条短原件只支持分项存储/传输可用，不把本协议当已经执行的试验。当前不连接设备、不新采、不改变手机/手表设置，不发布新的安装包。

## 已能确认的接口边界

小米公开[传感器文档](https://iot.mi.com/vela/quickapp/zh/features/system/sensor.html)明确列出S5支持subscribeAccelerometer，提供XYZ及game/ui/normal回调请求档，约20/60/200ms。没有在这一接口返回表声明硬件时间戳，XYZ单位也未在该表注明。文档没有列出通用subscribe、DATA_TYPES、getRecentData；缺少文档不是已证明运行时不存在。

固定公开参考源码open-vela/frameworks_runtimes_feature@e20440fe7d970609bd3f02e9335b1a85e4fcb148：专用AccelerometerRet为int XYZ、回调遍历datalen对应的若干sensor_accel；通用路径用double构造XYZ、档位是low/mid/high，在相关回调中没有看到同样的datalen遍历。不能把它当专用接口的直接替代：同一批数据是否会保留、S5是否导出、返回数值/单位/时间语义均待核。参考实现与本机固件对应未建立。

Date.now是JS回调读取的墙钟毫秒。用更细的JS时钟也不自动获得硬件事件时间；不得将同毫秒回调均匀拆成20ms、插值补硬件时间或按game档回填序列。

公开[亮度文档](https://iot.mi.com/vela/quickapp/zh/features/system/brightness.html)有setKeepScreenOn，但此页没有S5支持矩阵。当前App没声明system.brightness，也没调用常亮。未来若采用它，只能作为明确记录的前台试验条件，必须记录请求/回调/释放；不能混入默认记录或拿它证明后台自然可持续。

## 既有10秒记录不能解释什么

应用记录到三段hidden，共2233ms；111个hidden样本与事件窗口相符。visible→visible内也有15个>100ms间隔，因此页面隐藏不足以独自解释全部交付抖动。用户对实际熄屏/切页不确定，应用生命周期不是外部屏幕电源/冻结证据。这些只是同一个墙钟的内部一致性，不能反过来证明时间准确。

## 下一轮只做一种能力探测

先由Codex核对DS的只读反馈和公开接口依据，再准备独立源码候选；原记录器与接收器均保持。先不做分钟、后台或新增物理量。

1. 第一阶段只检查目标加速度接口的可调用性/类型与数据类型常量；不订阅、不读其它传感器、不调用未文档化reserved标志。只记录受控字段名/类型与错误码，不收账号/位置等数据。单次异常/卡住即停止该候选，不自动尝试另一变体。是否进行这一步仍须以后明确安排，不视为本轮已执行。
2. 若实际确认存在普通可用的通用加速度接口，另做一条最短独立短试，与专用接口分开运行；不同时订阅、不共用会话。原样保留返回的数值及实际存在的时间字段，附接口名称/字段定义/档位命名空间，不能把low/mid/high偷换成game/ui/normal。
3. 验收只判断可用性、原始字段是否保留、数量/回调分组、错误与完整运输。不因为出现小数就称精度提升，不因为有timestamp字样就称硬件单调时间。若通用接口不存在或字段仍不满足，明确记录普通入口的边界，保持原三轴路线；不通过提权/固件替换救结果。

## 之后才做可见性与更长记录

先把单位/时间语义说明白，再单独安排可外部核对的前台静止短试与页面切换短试，一次只变一个条件。用户不能确定现场条件时保持unknown，不追补为全程亮屏。分钟级、三档设置、标签、回收/恢复、退出重进各自另验；旧科研记录不用于删除试验。所有功能通过也不能直接宣称HAR、同步或空间泄露结果。

若腕部最终只有较粗的三轴/回调时间，只能围绕实际可读输入重新评估研究用途，不能预先保证融合增益或纯手机备选论文成立。
