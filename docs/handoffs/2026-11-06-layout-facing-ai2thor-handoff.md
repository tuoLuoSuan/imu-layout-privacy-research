## 3. 底层不可观测量：绝对朝向

六轴无磁力计 → 绕竖直轴的绝对转角不可观测。这是硬件信息缺口，不是算法缺陷。因此：

- 房间坐标系与轨迹坐标系之间的**旋转角是自由参数**
- 本方法用两条物理约束反解：① 整条轨迹必须装进 2.84×4.045 ② 从躺点到对面墙必须是正常床长（1.85–2.30 m）
- 扫描 -260°…-120°，在房内比例 83% 的平台是 -209°…-191°，**在这个平台内椅子锚点移动 0.7 m** —— 即旋转角本身欠定（±8°）
- 最终选择靠「起点钉 S=(0.825, 3.845)」+ 手臂约束共同收窄

## 4. 「用朝向判断家具贴哪面墙」的思路与三条路线的实测结果

### 4.1 用户的假设

> 「通过我面向哪里就能知道这个家具是在哪个墙上？就比如说我们那个柜子，它为什么是在那个墙，而不是在底下那个墙。」

### 4.2 路线 1：动作前 1.5 s 的走向当朝向代理

| 动作 | 走向角度 | 指向墙 | 真值 | |
|---|---|---|---|---|
| 坐下 12.5 s | +13.9° | 右墙 | 左墙 | ❌ |
| 拉柜门 20.5 s | 167.2° | 左墙 | 左墙 | ✅ |
| 躺下 34.5 s | 84.5° | 上墙 | 上墙 | ✅ |

**但动作前位移只有 0.06–0.35 m。** 把窗口从 1.5 s 换到 5 s，三个方向**全部翻转**（柜 167°→-62°、躺 84°→61°、坐 14°→-85°）。→ 不可用。

### 4.3 路线 2：陀螺仪积分出手机姿态（失败，已验证）

脚本：`phone_orient.py`、`facing_gyro.py`、`gyro_check.py`、`gyro_bias.py`

- 用 t0 附近加速度对齐重力后积分陀螺（6801 点 / 57.5 s / 中位间隔 8.4 ms）
- **验证不通过**：把「轨迹行进方向」与「陀螺积分偏航」逐点相减，理论上是常数，实测**标准差约 80 度**
- 原因：手机拿在手里会摆，**手机朝向 ≠ 身体朝向**
- 顺带查零偏：用速度 <0.05 的段估计，但那些段的陀螺本身 std 达 0.31/0.45/0.78 rad/s，说明并不静止，零偏估不准

**结论：手持六轴陀螺积分不能得到可用的身体朝向。**

### 4.4 路线 3（最终采用）：手臂够得着

脚本：`reach_check.py`

柜锚点在房间坐标 (1.25, 0.54)，家具深 0.60：

| 墙 | 站到该墙家具前沿的距离 | 是否在手臂 0.40–0.75 m 内 |
|---|---|---|
| 左墙 x=0 | 0.65 m | ✅ |
| 下墙 y=0 | 0.06 m | ❌（人会站进柜子里） |
| 右墙 x=2.84 | 0.99 m | ❌ |
| 上墙 y=4.045 | 2.91 m | ❌ |

**四面墙只有一面成立 → 柜子必在左墙。** 这是几何约束，不是打分。

坐锚点 (1.22, 1.27)：左 0.62、下 0.67 都成立，二义 → 靠「桌柜连体 + 椅子正对桌子」消解。

因此在 `reconstruct_v4.py` 里写的是：

```python
dist = {'left': ca[0], 'right': (W-ca[0]), 'down': ca[1], 'up': (L-ca[1])}
ok = [k for k, d in dist.items() if ARM[0]+DEPTH <= d <= ARM[1]+DEPTH]
if len(ok) != 1: return None      # 只有唯一解才接受
```

### 4.5 关于「朝向」这一路线的最终判断

- **绝对朝向**：两种设备都不可知（无磁力计）
- **身体朝向**：手持场景下陀螺积分不可用（§4.3 已验证失败）
- **能替代朝向的**：**手臂够得着的几何约束**（§4.4），它给出同样的结论且更稳

## 5. AI2-THOR 能做什么

网址：https://ai2thor.allenai.org/ ｜ PyPI: `ai2thor 5.0.0`（客户端 67 KB；首次运行会下载 Unity 场景包）

### 5.1 它是什么

Unity 室内场景模拟器，内置 120 个精装修房间（厨房/客厅/卧室/卫生间）。三条核心能力：

1. 每个物体都有精确 3D 包围盒、位置、朝向、类别：`event.metadata['objects']`
2. 可渲染 RGB + 深度 + 实例分割 + 语义分割
3. 有 agent 可在场景内导航

### 5.2 对应本项目的两个阶段

| | 第一阶段（稀疏语义图） | 第二阶段（稠密语义图） |
|---|---|---|
| AI2-THOR 提供 | 每个场景**本身**就是一张稀疏语义图（每件家具带标签的盒子） | 渲 depth + instanceSegmentation，反投影成带标签稠密点云 |
| 用途 | 当作 **ground truth**，检验从 IMU 反推的布局对不对 | 当作真值 / 点云分割模型的训练数据 |
| 解决什么问题 | 现在只有 1 间房，任何结论都是孤证 | 复杂场景（厨房几十个碗碟）人工标不了，渲一遍就有 |

### 5.3 它做不到什么（必须写清）

**AI2-THOR 不产生 IMU。** 它是场景模拟器，不是传感器模拟器。因此：

- 喂给重建器的路径是**无噪声**的：没有手持摆动、没有 RoNIN 漂移
- 在它上面做实验，验证的是**「布局推理规则是否普适」**，不是「里程计精度」
- 若走「合成 IMU」路线，需要注意 RoNIN 是在真实 IMU 上训练的，仿真加速度过于干净，结论不能外推到真机
- 真实 IMU 的验证仍然只有 s-59d570ee 这一条

## 6. 下一步建议（三条，按优先级）

### P0｜用 AI2-THOR 做布局泛化实验（1–2 天）

1. 遍历场景，挑出含 bed / desk / chair / cabinet 的房间
2. 从 `metadata['objects']` 读包围盒 → 生成 2D 俯视真值图
3. 用 `sim_layouts.py` 里的 A* 在平面图上生成「门口→椅→桌柜→床尾→门口」路径与四个动作点
4. 喂给 `reconstruct_v4.py` 的规则，与真值比误差
5. 产出：**N 间房的平均误差 + 失败率 + 失败类型**

这直接回答目前最缺的一个问题：这套规则是不是只对那一间房有效。

### P1｜稠密语义图真值（1 天）

从几个视角渲 depth + instanceSegmentation，用相机内外参反投影到世界坐标，每点带类别。产出第二阶段真值，也可用于训点云语义分割。

### P2｜补齐自身录音的可用率（低成本）

现有三条录音，只有一条首尾 2.5%。再录 2–3 条首尾 <3% 的，才能说方法稳定，而不是碰上了好数据。

## 7. 请 GPT 重点审的四件事

1. **§4.4 的手臂约束是否成立为「唯一解」**：它依赖「人站在家具正前方一臂距离」这个假设。若人在斜前方伸手，距离会变大，唯一性会破。这个假设在 AI2-THOR 实验里能否被系统性检验？
2. **§3 的旋转欠定（±8°）能否被 AI2-THOR 实验暴露**：如果能，说明方法在别的房间会失效；如果不能，说明真实数据上的 ±8° 是另一回事，需要单独解释。
3. **§5.3 的边界是否成立**：把无噪声路径喂给布局推理器，结论能推广到真实 IMU 吗？还是必须同时做噪声注入（尺度 0.9–1.1、每步漂移、朝向漂移）才能对比？
4. **第一阶段 / 第二阶段的划分是否合理**：目前第一阶段由 IMU 恢复、第二阶段完全由雷达提供。如果要求两个阶段都出自同一套输入，是否只能在第一阶段之后用「家具目录 + 先验高度」补齐，而那样算不算恢复？
